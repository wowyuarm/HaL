# Workspace Layout

**Status:** Active

This document defines the canonical `~/.hal/` layout and the cleanup policy for
legacy residue created by earlier iterations.

## Why This Exists

HaL has changed its workspace structure multiple times. The result is familiar:
some paths are current, some are compatibility aliases, and some are just
leftovers from old designs or ad hoc tooling.

This document makes one thing explicit:

- what is durable source-of-truth data
- what is derived or rebuildable runtime state
- what counts as legacy drift and should be migrated away

## Canonical Layout

```text
~/.hal/
  system/
    SOUL.md
    INSTRUCTIONS.md
    MEMORY.md
    config.yaml
    auth.yaml
    secrets.yaml

  work/
    threads/{slug}/
      THREAD.yaml
      BRIEF.md
      episodes/
      refs/
    sessions/{session_id}/
      manifest.json
      working-log.jsonl
    inbox/

  runtime/
    logs/
    resume/
    metrics/
    indexes/

  capabilities/
    skills/

  data/
    artifacts/
    media/
      received/

  projects/
  scripts/
  tmp/
```

## Data Classes

### 1. Durable collaboration data

These are the real state of the system. They should be inspectable, portable,
and never treated as disposable cache.

- `system/MEMORY.md`
- `work/threads/**`
- `work/sessions/**`
- `work/inbox/**`

### 2. Runtime and derived state

These matter operationally, but they are not the semantic source of truth.
They can usually be rebuilt from durable state or regenerated by future runs.

- `runtime/resume/**`
- `runtime/logs/**`
- `runtime/metrics/**`
- `runtime/indexes/**`

### 3. User-facing generated data

These are artifacts and media produced or received during use.

- `data/artifacts/**`
- `data/media/**`

## Cleanup Policy

### Canonical path wins

When a legacy path and a canonical path both exist, the canonical path is the
target model. Do not add more call sites that read from the legacy location.

### Safe auto-migrations only

Automatic migration may move a legacy path only when the target canonical path
does not already exist. If both exist, that is a manual merge case.

### User-authored system docs are not auto-rewritten

`SOUL.md`, `INSTRUCTIONS.md`, and `MEMORY.md` may contain stale references.
HaL may report those problems, but should not silently rewrite the files during
workspace migration.

## Known Legacy Patterns

These are considered drift and should be migrated or removed over time:

- `~/.hal/config.yaml` -> `system/config.yaml`
- `~/.hal/auth.yaml` -> `system/auth.yaml`
- `~/.hal/secrets.yaml` -> `system/secrets.yaml`
- `~/.hal/skills/` -> `capabilities/skills/`
- `~/.hal/media/received/` -> `data/media/received/`
- `runtime/sessions/` as a resume bucket; detached snapshots now live in `runtime/resume/`

## Naming Boundaries

To keep future refactors clean, use these distinctions:

- `system memory` means `system/MEMORY.md`: stable long-term facts
- `thread continuity` means `THREAD.yaml + BRIEF.md + episodes + session evidence`
- `recall index` means searchable derived indexes over durable thread/session outputs

Do not collapse all three into one vague "memory system" bucket in code or docs.
